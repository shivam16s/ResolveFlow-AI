FEATURE 1: MULTI-ISSUE INTENT DETECTION
================================================================================

PURPOSE
-------
Detect when a customer message contains more than one distinct issue so that the
agent can queue and address each issue rather than answering only the first one.

Example input:
  "I was charged twice this month and my internet is still not working. I want
   to cancel now."

Expected detection output:
  Issue 1: Billing dispute (duplicate charge)
  Issue 2: Service outage (internet not working)
  Issue 3: Cancellation intent (churn risk)

RESEARCH BASIS
--------------
τ²-bench (arXiv 2506.07982): "Evaluating Conversational Agents in a Dual-Control
Environment"

KEY ALGORITHM FROM τ²-BENCH
-----------------------------
τ²-bench models the support conversation as a Decentralized Partially Observable
Markov Decision Process (Dec-POMDP) where:

  State S: shared world state (database rows, flags, diagnostic results)
  Observations O_agent, O_user: each party sees a partial view of S
  Actions A_agent: tool calls + utterances
  Actions A_user: tool calls (e.g., router restart) + utterances
  Reward R: task completion verified against goal state

The paper introduces a compositional task generator that creates tasks by
combining atomic sub-tasks. This directly informs our multi-intent detection:
each sub-task (billing, outage, cancellation) is an atomic intent component.

From the paper abstract:
  "A compositional task generator that programmatically creates diverse,
   verifiable tasks from atomic components, ensuring domain coverage and
   controlled complexity."

IMPLEMENTATION
--------------

Step 1 — Intent Classifier
  Input: raw customer message
  Model: use an LLM with a structured output prompt

  Prompt design:
  ---------------------------------------------------------------
  You are an intent detector for a telecom support agent.
  Given the customer message, extract ALL distinct issues.
  Return a JSON array of intents from:
    ["billing_dispute", "duplicate_charge", "service_outage",
     "router_issue", "plan_change", "cancellation_intent",
     "refund_request", "technician_request", "general_query"]

  Customer message: "{message}"

  Output format:
  {
    "intents": ["intent1", "intent2"],
    "primary_intent": "intent1",
    "cancellation_risk": true/false,
    "urgency": "high/medium/low"
  }
  ---------------------------------------------------------------

Step 2 — Issue Queue
  Store detected intents in an ordered queue:
    issue_queue = [
      {"intent": "duplicate_charge", "status": "pending", "priority": 1},
      {"intent": "service_outage",   "status": "pending", "priority": 2},
      {"intent": "cancellation_intent", "status": "pending", "priority": 3}
    ]

Step 3 — Sequential Resolution Loop (from τ²-bench Dec-POMDP model)
  For each issue in queue:
    a. Retrieve relevant memory for that issue
    b. Retrieve relevant policy for that issue
    c. Call required tools for that issue
    d. Generate partial resolution response
    e. Mark issue as resolved or escalated
    f. Proceed to next issue

Step 4 — Acknowledgment response
  After detection, acknowledge ALL detected issues:
    "I can see you have three concerns: a billing issue, a service problem,
     and you're thinking about cancelling. Let me address each one."

DATA STRUCTURES
---------------
  ConversationState {
    session_id: str
    customer_id: str
    raw_message: str
    issue_queue: List[Issue]
    current_issue: Issue
    resolved_issues: List[Issue]
    escalation_required: bool
  }

  Issue {
    intent: str
    status: "pending" | "in_progress" | "resolved" | "escalated"
    priority: int
    tools_called: List[str]
    resolution: str | null
  }

FEATURE 2: CUSTOMER MEMORY LAYER
================================================================================

PURPOSE
-------
Maintain a three-tier memory store so the agent never asks the customer to
repeat context that was already shared in past or current sessions.

Memory tiers:
  Stable memory:  customer plan, preferences, language
  Episodic memory: previous complaints, tickets, credits, refunds
  Session memory: what the customer already said in this conversation

RESEARCH BASIS (PRIMARY)
------------------------
LongMemEval (arXiv 2410.10813): "Benchmarking Chat Assistants on Long-Term
Interactive Memory"

KEY ALGORITHM FROM LONGMEMEVAL
--------------------------------
LongMemEval identifies five core memory capabilities that a long-term assistant
must possess:
  1. Information Extraction — pulling facts from past sessions
  2. Multi-session Reasoning — connecting facts across different sessions
  3. Temporal Reasoning — tracking when something happened, recency, order
  4. Knowledge Updates — handling when a customer's situation changes
  5. Abstention — knowing when there is not enough memory to answer safely

The paper proposes a three-stage memory processing framework:

  Stage 1: INDEXING
    Split long session history into atomic memory units (one fact per unit).
    Each memory unit is indexed with:
      - embedding vector (for semantic search)
      - metadata: timestamp, session_id, topic, customer_id
      - fact type: stable / episodic / preference

  Stage 2: RETRIEVAL
    For a new query, expand it using:
      a. Fact-augmented key expansion: add derived facts to the search query
         Example: "billing issue" → "billing issue OR duplicate charge OR invoice"
      b. Time-aware query expansion: add temporal anchors
         Example: "last week's complaint" → include date range in search
    Run vector similarity search + BM25 keyword search
    Merge results by rank fusion

  Stage 3: READING
    Pass retrieved memory units to the LLM with a structured context template.
    Instruct the LLM to cite which memory unit it used.
    If no relevant memory found → abstain rather than hallucinate.

Key finding: commercial systems drop ~30% accuracy in sustained multi-session
interactions when memory is not structured. This is why ResolveFlow uses
explicit memory lanes.

RESEARCH BASIS (SECONDARY)
----------------------------
HippoRAG (arXiv 2405.14831): "Neurobiologically Inspired Long-Term Memory for LLMs"

KEY ALGORITHM FROM HIPPOGRAPH
-------------------------------
HippoRAG applies the hippocampal memory indexing theory to build a graph-based
memory index for multi-hop memory retrieval.

OFFLINE INDEXING PHASE (run when new session data arrives):
  1. For each session transcript or customer event (passage p):
     a. Use LLM L to extract named entities + OpenIE triples (subject, relation,
        object). This is done via 1-shot prompting.
        Example triples extracted from "customer reported outage on May 14":
          (customer_Rahul, reported_outage, May_14)
          (outage, location, Chennai_Zone_04)
     b. Add noun phrase nodes N and relation edges E to the knowledge graph KG.
     c. Use retrieval encoder M to add synonymy edges E' between nodes whose
        cosine similarity exceeds threshold τ = 0.8.
        Example: ("duplicate_charge", "double billing") get an E' edge.
  2. Build matrix P of size |N| × |P|:
     P[i][j] = number of times noun phrase node i appears in passage j

ONLINE RETRIEVAL PHASE (run at query time):
  1. Use LLM to extract named entities Cq = {c1, …, cn} from query q.
  2. Encode each ci with retrieval encoder M.
  3. Find closest node in KG to each ci → query nodes Rq = {r1, …, rn}.
  4. Set personalized probability vector n_hat over all N:
       n_hat[ri] = (1/n) * node_specificity(ri) for ri in Rq
       n_hat[other] = 0
     where node_specificity(i) = |P_i|^-1   (i.e., inverse passage frequency)
  5. Run Personalized PageRank (PPR) with damping factor 0.5:
       n_hat' = PPR(KG, n_hat)
  6. Compute passage scores:
       p_hat = n_hat' × P  (matrix multiply: |N| vector × |N|×|P| matrix)
  7. Return top-k passages ranked by p_hat.

This allows "Rahul had an outage last week and received a credit" to be
retrieved even when the query only mentions "Rahul" and "credit", because the
graph path Rahul → outage → credit is traversed in one PPR step.

Code architecture:
  class MemoryManager:
    def index_session(session_transcript, customer_id):
      # LongMemEval Stage 1: decompose into atomic memory units
      units = decompose_to_memory_units(session_transcript)
      for unit in units:
        embedding = embed(unit.content)
        store_in_vector_db(customer_id, unit, embedding)
        # HippoRAG: extract triples and build/update KG
        triples = llm_extract_openie_triples(unit.content)
        update_memory_graph(customer_id, triples, unit.memory_id)

    def retrieve(query, customer_id, top_k=5):
      # LongMemEval Stage 2: query expansion
      expanded_query = fact_augmented_expansion(query)
      temporal_query = time_aware_expansion(query)
      # Vector search
      vector_results = vector_db.search(customer_id, expanded_query, k=top_k*2)
      # HippoRAG: graph search
      query_entities = llm_extract_named_entities(query)
      graph_results = hipporag_ppr_retrieval(customer_id, query_entities, top_k)
      # Merge by rank fusion
      return rank_fusion(vector_results, graph_results, top_k)

    def read(retrieved_units, query):
      # LongMemEval Stage 3: structured reading with abstention
      context = format_memory_context(retrieved_units)
      return llm_read_with_citation(context, query)

Memory update triggers:
  - End of conversation: index full session
  - Mid-session: update session memory after each turn
  - Plan change event: update stable memory
  - Credit/refund event: add to episodic memory

FEATURE 3: POLICY-GROUNDED RETRIEVAL
================================================================================

PURPOSE
-------
Retrieve the correct policy document before answering any risky question
(refund, credit, cancellation, escalation). Assess retrieval quality and
retry or fall back if the retrieved content is not reliable.

RESEARCH BASIS (PRIMARY)
------------------------
Self-RAG (arXiv 2310.11511): "Learning to Retrieve, Generate, and Critique
through Self-Reflection"

KEY ALGORITHM FROM SELF-RAG
-----------------------------
Self-RAG introduces four types of "reflection tokens" that control when to
retrieve and how to evaluate retrieved content:

  [Retrieve]:  yes | no | continue
    → Should the model retrieve passages for this segment?

  [IsRel]:     relevant | irrelevant
    → Is the retrieved passage relevant to the input?

  [IsSup]:     fully supported | partially supported | no support
    → Does the passage support the generated text?

  [IsUse]:     1 | 2 | 3 | 4 | 5
    → How useful is this passage for answering the query?

INFERENCE ALGORITHM (how the agent decides to retrieve and score):
  For each generation segment yt:
    1. Predict [Retrieve] token from {yes, no, continue}
    2. If [Retrieve] = yes:
         Retrieve top K passages D = {d1, …, dK} from vector store
         For each passage di in parallel:
           a. Predict [IsRel](x, di)  — relevance check
           b. Generate segment yt | x, di
           c. Predict [IsSup](x, di, yt) — support check
           d. Score = p(yt | x, di, y<t) + Σ wG * sG  (weighted reflection scores)
    3. Select passage d* with highest final score
    4. Predict [IsUse](x, yt*) on final output
    5. If [IsUse] < 3 → trigger CRAG corrective flow (see below)

Training note: a critic model (fine-tuned on GPT-4 labels) scores the
reflection tokens. In our case we approximate this with LLM-as-judge prompts.

RESEARCH BASIS (SECONDARY)
---------------------------
CRAG (arXiv 2401.15884): "Corrective Retrieval Augmented Generation"

KEY ALGORITHM FROM CRAG
-------------------------
CRAG adds a retrieval evaluator that classifies retrieved documents into three
confidence states and takes different actions for each:

  Inputs: query x, retrieved documents D = {d1, …, dk}

  For each (x, di) pair, evaluator E produces a confidence score in [-1, 1].

  STEP 1 — EVALUATE
    score_i = E(x, di)  for each retrieved doc
    max_score = max(score_i for all i)

  STEP 2 — ROUTE by threshold (empirically set; paper uses 0.59 / -0.99):

    CASE A: CORRECT   (max_score > upper_threshold)
      → Internal knowledge path:
        1. Decompose each doc into fine-grained "knowledge strips"
           (sentence or paragraph-level chunks)
        2. Re-score each strip with E(x, strip)
        3. Keep only strips with score > threshold
        4. Recompose kept strips → refined internal knowledge
        5. Pass to generator

    CASE B: INCORRECT (all scores < lower_threshold)
      → External knowledge path:
        1. Discard all retrieved docs
        2. Rewrite query: "convert query to short web-search keywords"
           Example: "Can I get a service credit?" → "telecom service credit policy"
        3. Execute web search / search secondary corpus
        4. Apply same strip decomposition and re-scoring
        5. Pass to generator

    CASE C: AMBIGUOUS (scores between thresholds)
      → Combine internal + external:
        1. Use Case A strips from original docs
        2. Also do the Case B web search
        3. Concatenate both refined sources
        4. Pass to generator

  STEP 3 — GENERATE
    Generator G produces final answer from refined knowledge + query.

Evaluator: the paper uses a T5-large (770M param) model fine-tuned on
relevance pairs. For ResolveFlow MVP, use an LLM-as-judge prompt instead.

--------------

class PolicyRetriever:
  policy_docs = [
    "service_credit_policy",
    "refund_policy",
    "duplicate_charge_policy",
    "cancellation_policy",
    "technician_visit_policy",
    "plan_change_policy",
    "escalation_policy"
  ]

  def retrieve(query, k=5):
    # Step 1: Self-RAG — decide whether to retrieve
    should_retrieve = llm_predict_retrieve_token(query)
    if not should_retrieve:
      return None, "no_retrieval"

    # Step 2: Vector search over policy_docs
    candidates = vector_db.search(policy_collection, query, k=k)

    # Step 3: CRAG — evaluate each retrieved doc
    scored_docs = []
    for doc in candidates:
      score = llm_evaluate_relevance(query, doc)
      scored_docs.append((score, doc))

    max_score = max(s for s, _ in scored_docs)
    UPPER = 0.6
    LOWER = 0.2

    # Step 4: CRAG routing
    if max_score > UPPER:
      # CORRECT path
      strips = decompose_to_strips(best_doc)
      scored_strips = [(llm_evaluate_relevance(query, s), s) for s in strips]
      refined = [s for score, s in scored_strips if score > UPPER]
      return refined, "correct"
    elif max_score < LOWER:
      # INCORRECT path — retry with keyword rewrite
      keywords = llm_rewrite_query_to_keywords(query)
      new_candidates = vector_db.search(policy_collection, keywords, k=k)
      strips = decompose_to_strips(new_candidates)
      scored_strips = [(llm_evaluate_relevance(query, s), s) for s in strips]
      refined = [s for score, s in scored_strips if score > LOWER]
      return refined, "corrected"
    else:
      # AMBIGUOUS path — combine both
      internal_strips = crag_correct_path(best_doc, query)
      external_strips = crag_incorrect_path(query)
      return internal_strips + external_strips, "ambiguous"

  def generate_answer(query, refined_docs):
    # Self-RAG: predict [IsSup] and [IsUse] for each doc
    for doc in refined_docs:
      sup_score = llm_predict_issup(query, doc)
      use_score = llm_predict_isuse(query, doc)
    # Generate with citation
    return llm_generate_with_citation(query, refined_docs)

  4. Store in ChromaDB collection named "resolveflow_policies"

FEATURE 4: POLICY GRAPH / POLICY DAG
================================================================================

PURPOSE
-------
Route high-risk actions through a deterministic rule graph instead of letting
the LLM freely decide. A Policy DAG checks pre-conditions before each action.

Example DAG for "Apply Service Credit":
  Was outage verified?
    → NO  → Deny credit, suggest ticket
    → YES → Was outage > 6 hours?
               → NO  → Apply partial credit (≤ ₹100)
               → YES → Has credit been applied this billing cycle?
                          → YES → Escalate to human (cannot double-credit)
                          → NO  → Is credit amount ≤ ₹500?
                                     → YES → Auto-apply
                                     → NO  → Escalate for approval

RESEARCH BASIS (PRIMARY)
------------------------
JourneyBench / Beyond IVR (arXiv 2601.00596): "Benchmarking Customer Support
LLM Agents for Business-Adherence"

KEY ALGORITHM FROM JOURNEYBENCH
---------------------------------
JourneyBench represents support policies as directed graphs (called "user
journeys") and introduces two agent designs:

  SPA — Static-Prompt Agent:
    The agent receives the full policy document as a static prompt.
    No explicit structure; relies on LLM to follow rules.
    Result: inconsistent rule compliance.

  DPA — Dynamic-Prompt Agent:
    The policy graph is traversed dynamically. At each node:
      1. Evaluate the guard conditions of that node (tool call or LLM check)
      2. Based on result, select the outgoing edge
      3. Load only the policy text for the current node into context
      4. Proceed to next node
    Result: DPA significantly boosts adherence vs SPA.
            Even GPT-4o-mini with DPA outperforms GPT-4o with SPA.

Key insight from JourneyBench: "Structured orchestration matters more than
model size." A smaller model with a policy graph beats a larger model without one.

Metric: User Journey Coverage Score (UJCS) — fraction of required policy nodes
visited in the correct order during a conversation.

RESEARCH BASIS (SECONDARY)
---------------------------
SOP-Bench (arXiv 2506.08119): "Complex Industrial SOPs for Evaluating LLM Agents"

KEY INSIGHT FROM SOP-BENCH
----------------------------
SOP-Bench tests agents on 2,000+ tasks from human-authored Standard Operating
Procedures (SOPs) across 12 business domains. Key findings:
  - LLM agents frequently skip required steps or call the wrong tool
  - Function-Calling (FC) agents and ReAct agents fail differently
  - No single model dominates; best performance ranges from 57% to 100% by domain
  - Step-level validation (checking each SOP step, not just final output) is
    necessary to catch partial failures

This motivates ResolveFlow's Policy Graph to validate each step individually,
not just the final outcome.

IMPLEMENTATION
--------------

Define policy DAG nodes as Python dataclasses:

  @dataclass
  class PolicyNode:
    node_id: str
    description: str
    condition_type: "tool_check" | "llm_check" | "threshold_check"
    condition_args: dict
    edges: dict[str, str]   # {condition_result: next_node_id}

Example: Service Credit DAG

  policy_dag = {
    "check_outage_verified": PolicyNode(
      condition_type="tool_check",
      condition_args={"tool": "check_outage_status", "field": "verified"},
      edges={"true": "check_outage_duration", "false": "deny_credit"}
    ),
    "check_outage_duration": PolicyNode(
      condition_type="threshold_check",
      condition_args={"tool": "check_outage_status", "field": "duration_hours",
                      "operator": ">", "value": 6},
      edges={"true": "check_prior_credit", "false": "apply_partial_credit"}
    ),
    "check_prior_credit": PolicyNode(
      condition_type="tool_check",
      condition_args={"tool": "get_invoice_history",
                      "field": "credit_this_cycle"},
      edges={"false": "check_credit_amount", "true": "escalate_double_credit"}
    ),
    "check_credit_amount": PolicyNode(
      condition_type="threshold_check",
      condition_args={"field": "requested_amount", "operator": "<=",
                      "value": 500},
      edges={"true": "auto_apply_credit", "false": "escalate_approval"}
    ),
    "auto_apply_credit": PolicyNode(action="apply_credit"),
    "escalate_double_credit": PolicyNode(action="handoff_human"),
    "escalate_approval": PolicyNode(action="handoff_human"),
    "deny_credit": PolicyNode(action="generate_denial_response"),
    "apply_partial_credit": PolicyNode(action="apply_credit", args={"max": 100})
  }

class PolicyGraphValidator:
  def run(self, policy_name, context):
    dag = load_dag(policy_name)
    current_node = dag.start_node
    path = [current_node]
    while not is_leaf(current_node):
      result = evaluate_condition(current_node, context)
      next_node = dag[current_node].edges[result]
      path.append(next_node)
      current_node = next_node
    action = dag[current_node].action
    ujcs = len(path) / len(dag)  # User Journey Coverage Score
    return action, path, ujcs

FEATURE 5: TOOL-CALLING LAYER
================================================================================

PURPOSE
-------
Use explicit mock backend API calls instead of hallucinating account state.
Every claim about a customer account must be backed by a tool call result.

RESEARCH BASIS (PRIMARY)
------------------------
τ-bench (arXiv 2406.12045): "A Benchmark for Tool-Agent-User Interaction in
Real-World Domains"

KEY ALGORITHM FROM τ-BENCH
---------------------------
τ-bench creates a benchmark where a language agent is given:
  - A set of domain-specific API tools
  - Policy guidelines (rules about when/how to use tools)
  - A simulated user (driven by a language model)

The agent must complete tasks through multi-turn conversation + tool calls.

Evaluation:
  1. At the end of each conversation, compare actual database state to the
     annotated goal state.
  2. Task success = (actual_state == goal_state)
  3. Reliability metric: pass^k
     pass^k = (number of trials with at least one success) / k
     → measures consistency, not just peak performance

Key findings:
  - GPT-4o succeeds on <50% of tasks
  - pass^8 drops to <25% in retail domain
  - Agents frequently call tools in wrong order or skip required tool calls

This motivates ResolveFlow's tool call logging, sequential enforcement, and
explicit step validation.

RESEARCH BASIS (SECONDARY)
---------------------------
Beyond Browsing: API-Based Web Agents (arXiv 2410.16464)

KEY INSIGHT FROM API-BASED AGENTS
-----------------------------------
The paper compares three agent types on WebArena tasks:
  1. Browsing Agent (HTML/DOM interaction only)
  2. API-Calling Agent (API calls only)
  3. Hybrid Agent (both APIs and browsing)

Results on WebArena:
  - API-Based Agents outperform Browsing Agents
  - Hybrid Agents achieve 38.9% success rate (SOTA among task-agnostic agents)
  - Improvement: >24% absolute improvement over browsing alone

Key finding: "When APIs are available, they present an attractive alternative
to relying on web browsing alone."

For ResolveFlow, this confirms: use explicit mock APIs, not LLM guess-work.

FEATURE 6: CLARIFICATION ENGINE
================================================================================

PURPOSE
-------
Ask targeted, high-value clarification questions instead of generic "please
clarify" prompts. Clarify only when a specific missing slot blocks action.

RESEARCH BASIS
--------------
τ²-bench (arXiv 2506.07982): "Evaluating Conversational Agents in a
Dual-Control Environment"

KEY INSIGHT FROM τ²-BENCH ON CLARIFICATION
---------------------------------------------
τ²-bench evaluates agents in a dual-control setting where both agent and user
must take actions. A key finding:

  "Our experiments show significant performance drops when agents shift from
   no-user to dual-control, highlighting the challenges of guiding users."

The paper provides fine-grained error analysis separating:
  - Reasoning errors (agent misunderstands the situation)
  - Communication errors (agent fails to guide the user to the right action)
  - Coordination errors (agent and user act on misaligned state)

This shows that clarification must be precise: ask for exactly the information
needed to take the next action, not a vague open question.

IMPLEMENTATION
--------------

Slot schema per intent:
  billing_dispute: {
    required: [customer_id, billing_period],
    optional: [specific_charge_amount]
  }
  service_outage: {
    required: [customer_id, location],
    optional: [outage_start_time, device_type]
  }
  cancellation_intent: {
    required: [customer_id, reason],
    optional: [alternative_plan_interest]
  }

Decision logic:
  def decide_next_action(intent, current_slots, memory, policy_context):
    missing_required = get_missing_required_slots(intent, current_slots)

    if len(missing_required) > 0:
      # Ask for the most critical missing slot first
      slot_to_ask = prioritize_slot(missing_required)
      return Action(
        type="ASK_CLARIFICATION",
        question=generate_targeted_question(intent, slot_to_ask),
        slot=slot_to_ask
      )

    elif has_enough_context_for_tool_call(intent, current_slots):
      return Action(type="CALL_TOOL", tool=select_tool(intent))

    elif policy_requires_human_approval(intent, current_slots):
      return Action(type="HANDOFF")

    else:
      return Action(type="ANSWER")

Question generation:
  Bad:  "Can you provide more details?"
  Good: "Was this charge on your broadband bill or your mobile add-on?"
  Good: "What location is experiencing the internet outage?"
  Good: "Are you looking to cancel completely, or would a plan downgrade help?"

The targeted question is generated by:
  f"Based on the customer's issue ({intent}) and the missing slot ({slot}),
   generate one specific question to get exactly {slot}.
   Do NOT ask about anything else. Be direct and helpful."

================================================================================
FEATURE 6A: GUIDED USER ACTION COORDINATOR
================================================================================

PURPOSE
-------
Manage the wait-verify loop when the resolution requires the customer to perform
a physical action (router reset, app restart, identity verification, meter read).
This is distinct from asking a question: the agent must pause, wait for the user
to complete an action in the real world, then re-run a diagnostic tool to verify
the outcome before proceeding.

RESEARCH BASIS
--------------
τ²-bench (arXiv 2506.07982): "Evaluating Conversational Agents in a
Dual-Control Environment"

KEY ALGORITHM FROM τ²-BENCH: DUAL-CONTROL INTERACTION
------------------------------------------------------
τ²-bench models support conversations as a Dec-POMDP where BOTH the agent AND
the user take actions in the world — not just exchange messages. The benchmark
explicitly includes tasks where:
  - Agent instructs user to perform a physical action
  - User performs the action (or claims to)
  - Agent must verify via tool call, not trust the claim

From the paper abstract:
  "We introduce tasks requiring coordinated actions across both agent and user,
   exposing a new class of coordination errors that existing benchmarks miss."

The paper identifies three error types that appear uniquely in dual-control:
  1. Reasoning errors      — agent makes wrong diagnosis
  2. Communication errors  — agent gives compound/unclear instructions
  3. Coordination errors   — agent proceeds without verifying user action

Key finding: agent success rates drop significantly vs. single-control baselines
specifically because of coordination errors (type 3). The fix is explicit state
machine management: never proceed until tool verification confirms the outcome.

IMPLEMENTATION
--------------

class GuidedActionCoordinator:
    """
    Manages the wait-verify loop when the user must perform a physical action.
    τ²-bench finding: agents degrade significantly when shifting from passive
    user to dual-control. Structured state machine prevents coordination errors.
    """

    STATES = ["INSTRUCTING", "WAITING", "VERIFYING", "RESOLVED", "FAILED"]

    def __init__(self):
        self.state = "IDLE"
        self.pending_action = None
        self.attempts = 0
        self.MAX_ATTEMPTS = 2

    def instruct(self, action_required: str, context: dict) -> str:
        """
        Generate a precise, single-step instruction.
        τ²-bench error taxonomy: 'communication errors' happen when agents
        give compound instructions. One step at a time only.
        """
        self.state = "WAITING"
        self.pending_action = action_required
        self.attempts += 1
        instruction = generate_single_step_instruction(action_required, context)
        # Log to audit trail: instruction issued, verification pending
        log_audit("guided_action_issued", action_required, context["customer_id"])
        return instruction

    def handle_user_report(self, user_message: str, context: dict) -> Action:
        """
        User reports completion. Bot re-runs diagnostic tool to verify.
        Never trust the claim — always verify with a tool call.
        This directly addresses τ²-bench coordination error type 3.
        """
        self.state = "VERIFYING"
        tool_result = rerun_verification_tool(self.pending_action, context)
        log_audit("guided_action_verified", tool_result, context["customer_id"])

        if tool_result.success:
            self.state = "RESOLVED"
            return Action(
                type="CONTINUE_RESOLUTION",
                evidence=tool_result,
                message=f"Confirmed — {tool_result.confirmation_message}"
            )
        elif self.attempts < self.MAX_ATTEMPTS:
            # Try once more with clearer instruction
            self.state = "INSTRUCTING"
            return Action(
                type="RETRY_INSTRUCTION",
                message=self.instruct(self.pending_action, context)
            )
        else:
            # Action didn't fix it after 2 attempts — escalate
            self.state = "FAILED"
            return Action(type="ESCALATE", reason="user_action_unresolved")

Action-to-tool mapping:
  router_reset        → rerun: run_router_diagnostic()
  identity_verify     → rerun: lookup_customer() with new token
  app_restart         → rerun: run_router_diagnostic() (same endpoint)
  meter_reading       → rerun: check_outage_status() for location

DEMO FLOW (the single most memorable moment in the demo video):
--------------------------------------------------------------

  Turn 1:
  Bot:  "Your router diagnostic shows weak signal (18 Mbps, expected 200 Mbps).
         Can you press the reset button on the back of the router for 10 seconds
         and let me know when the lights come back on?"

================================================================================
FEATURE 7: CONVERSATION HEALTH SCORE
================================================================================

PURPOSE
-------
Compute a real-time score (0–100) that tracks conversation quality and triggers
preventive action (clarification or handoff) before the conversation fails.

RESEARCH BASIS
--------------
Derived from τ-bench pass^k metric + τ²-bench error taxonomy + LongMemEval
abstention capability.

ALGORITHM
---------
Health Score = weighted sum of five dimensions:

  H = 0.30 * intent_confidence
    + 0.25 * (1 - missing_info_risk)
    + 0.20 * sentiment_score
    + 0.15 * (1 - loop_penalty)
    + 0.10 * knowledge_coverage

Component definitions:
  intent_confidence:   [0.0 – 1.0]
    = average confidence of detected intents (from classifier softmax)
    Low if ambiguous input, high if intent is clear

  missing_info_risk:   [0.0 – 1.0]
    = (required_slots_missing / total_required_slots) for current intent

  sentiment_score:     [0.0 – 1.0]
    = 1.0 – frustration_score
    frustration_score = LLM-classified sentiment (positive/neutral/frustrated/angry)
    angry → 0.9, frustrated → 0.6, neutral → 0.2, positive → 0.0

  loop_penalty:        [0.0 – 1.0]
    = 1.0 if same question asked by customer >= 3 times in session
    = 0.5 if same question asked 2 times
    = 0.0 otherwise

  knowledge_coverage:  [0.0 – 1.0]
    = fraction of required_tools already called successfully
    = retrieved_policy_confidence (from CRAG evaluator)

THRESHOLDS AND ACTIONS:
  H >= 70: ANSWER — proceed normally
  50 <= H < 70: ASK_CLARIFICATION — ask targeted question
  30 <= H < 50: PREPARE_HANDOFF — escalate warning, last chance to resolve
  H < 30: HANDOFF — warm human handoff now

IMPLEMENTATION
--------------
  def compute_health_score(conversation_state):
    ic = conversation_state.intent_confidence
    mr = len(missing_slots) / total_required_slots
    ss = 1.0 - sentiment_classifier(last_3_messages)
    lp = loop_detector(conversation_state.messages)
    kc = knowledge_coverage(conversation_state.tools_called,
                            conversation_state.retrieved_policies)

    score = (0.30 * ic + 0.25 * (1 - mr) + 0.20 * ss +
             0.15 * (1 - lp) + 0.10 * kc) * 100
    return round(score)

  def get_recommended_action(score):
    if score >= 70: return "ANSWER"
    elif score >= 50: return "ASK_CLARIFICATION"
    elif score >= 30: return "PREPARE_HANDOFF"
    else: return "HANDOFF"

CROSS-SESSION RELATIONSHIP SCORE
---------------------------------
Research basis: LongMemEval (arXiv 2410.10813) — multi-session temporal
reasoning + knowledge updates across sessions.
Theory basis: CASA (Computers Are Social Actors) — empathic responses after
past failures rebuild trust and reduce churn probability.

The in-session health score uses last_3_messages for sentiment. LongMemEval
explicitly documents a ~30% accuracy drop across multi-session interactions
when past session tone is ignored. The Relationship Score addresses this gap
by tracking sentiment trajectory ACROSS past sessions and feeding it into
session-start behavior — connecting Feature 2 (Memory), Feature 7 (Health),
and Feature 8 (Handoff) into a single coherent system.

  def compute_relationship_score(customer_id: str) -> float:
      """
      Computes a 0–100 score reflecting the customer's sentiment trajectory
      across ALL past sessions, not just the current one.
      Stored in episodic memory. Updated at session close.
      """
      past_sessions = memory_manager.retrieve(
          query="sentiment tone frustration complaint escalation",
          customer_id=customer_id,
          memory_type="episodic",
          top_k=5
      )
      if not past_sessions:
          return 75.0  # no history → assume neutral relationship

      # Weighted decay: most recent session weights most
      scores = [classify_session_sentiment(s) for s in past_sessions]
      weights = [0.5 ** i for i in range(len(scores))]  # exponential decay
      relationship_score = (
          sum(s * w for s, w in zip(scores, weights)) / sum(weights)
      )
      return round(relationship_score * 100, 1)

  # classify_session_sentiment returns [0.0 – 1.0]:
  #   resolved_happy  → 0.9
  #   resolved_neutral → 0.7
  #   unresolved_neutral → 0.4
  #   escalated_frustrated → 0.2
  #   escalated_angry → 0.1

Relationship score thresholds and session-start actions:
  > 65:  HEALTHY  — proceed normally, no special action
  40–65: DRIFTING — proactive check-in at session start:
    "I can see we've been in touch a few times recently. I want to make
     sure we fully resolve things for you today."
  < 40:  AT-RISK  — activate CASA empathy sequence BEFORE any resolution:
    "I can see you've had a frustrating experience with us. Before we get
     into the details, I want to acknowledge that and commit to resolving
     this completely."
    → Also pre-loads churn_risk = HIGH into customer context
    → Feature 8 handoff threshold lowered from H < 30 to H < 40

Relationship score storage and update:
  - Read at session start from episodic memory (Feature 2 memory layer)
  - Updated at session close: new entry added to episodic memory with
    session outcome classification
  - Displayed on dashboard: "Relationship Score: 29 → 58 (recovered)"

The health score is displayed live in the agent reasoning panel on the UI
(color-coded: green > 70, amber 50–70, red < 50).
The relationship score is shown separately as a session-start indicator
(color-coded: green > 65, amber 40–65, red < 40).

FEATURE 8: WARM HUMAN HANDOFF
================================================================================

PURPOSE
-------
Escalate to a human agent before the conversation fails, not after. Pass full
context so the customer never has to repeat themselves.

RESEARCH BASIS
--------------
τ-bench (arXiv 2406.12045) + τ²-bench (arXiv 2506.07982)

KEY INSIGHT
-----------
τ-bench defines task success as matching the goal database state after
conversation. If the AI agent fails to complete the goal state, a human must
step in. The paper measures "unnecessary escalation rate" and "late escalation
rate" as failure modes.

τ²-bench shows that in dual-control environments (where both agent and user act),
communication failures are distinct from reasoning failures. Warm handoff
addresses communication failures: the human agent receives the reasoning state.

TRIGGER CONDITIONS
------------------
  1. Policy exception required (amount > allowed threshold)
  2. Health score drops below 30
  3. Customer anger level = "high" for 2+ consecutive turns
  4. Same question loop: 3+ repeats without progress
  5. High-value customer at churn risk (risk_level = "critical")
  6. Tool failure on critical tool (e.g., apply_credit fails)
  7. Refund above auto-approval threshold (> ₹500)
  8. Customer explicitly requests human agent

HANDOFF PROCESS
---------------
  1. Detect trigger condition
  2. Generate Customer Context Card (Feature 9)
  3. Mark conversation for human queue
  4. Inform customer:
     "I'm connecting you to a specialist who has your full account details.
      You won't need to repeat anything."
  5. Insert conversation + context card into human_handoff_queue table
  6. Log handoff event in audit trail

FEATURE 11: AGENT EVALUATION HARNESS
================================================================================

PURPOSE
-------
Before demo day, validate all features with 10 scripted test scenarios and
8 metrics. Catch hallucinations, wrong tool calls, and policy violations early.

RESEARCH BASIS (PRIMARY)
------------------------
τ-bench (arXiv 2406.12045): defines evaluation as comparing final database
state vs. goal state, plus pass^k for reliability across trials.

KEY ALGORITHM FROM τ-BENCH EVALUATION
---------------------------------------
  For each test case c:
    1. Initialize mock database to known state S_initial
    2. Run agent through scripted conversation (simulated user)
    3. At end, read actual database state S_actual
    4. Compare S_actual to annotated S_goal
    5. task_success(c) = 1 if S_actual == S_goal else 0

  pass^k metric (for reliability):
    Run each test case k times with temperature > 0
    pass^k = (trials with at least 1 success) / k
    → Low pass^k means the agent is lucky, not reliable

  Policy compliance: also check that each action was preceded by the correct
  policy DAG traversal (UJCS > threshold).

RESEARCH BASIS (SECONDARY)
---------------------------
τ²-bench (arXiv 2506.07982): introduces fine-grained error decomposition:
  - Reasoning errors: wrong tool, wrong decision
  - Communication errors: failed to get needed info from user
  - Coordination errors: agent and user took inconsistent actions

IMPLEMENTATION
--------------

  ─────────────────────────────────────────────────────────────────────────

Note on policy compliance: unlike model-trust approaches where the LLM may or
may not follow a policy, ResolveFlow's PolicyGraphValidator enforces DAG
traversal structurally — the action is blocked at code level if the prerequisite
nodes have not been visited. Compliance is guaranteed, not prompted.

EVALUATION RUNNER:

  def run_evaluation():
    results = {}
    for case in test_cases:
      db.reset_to_initial_state(case.initial_state)
      for trial in range(K):
        response = agent.run(case.user_messages)
        final_state = db.read_state()
        success = (final_state == case.goal_state)
        results[case.id][trial] = success
      results[case.id]["pass_k"] = sum(results[case.id]) / K
    print_evaluation_report(results)
