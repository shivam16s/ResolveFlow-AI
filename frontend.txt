
Do deep research on FlowZint AI Hackathon 2026 frontend for ResolveFlow
Executive summary
ResolveFlow’s frontend should not look like a consumer chatbot with a hidden backend. It should look like a customer-care operations console that visibly demonstrates the exact qualities FlowZint says it rewards: innovation, real-world applicability, technical architecture, and documentation clarity. The official FlowZint portal also makes the submission constraints concrete: the project is submitted under one official track, teams can have up to four members, the public judging rubric is weighted across novelty, applicability, architecture, and documentation, and the final submission requires a public demo video, a public source-code repository, and a project description with minimum length; private or incomplete links can trigger rejection. That means your frontend must double as both product UI and judging evidence. 

For a Customer Care Bot entry, the fastest winning posture is a frontend that makes the hard parts of modern agent systems easy to see: multi-issue intake, long-term memory, evidence-backed retrieval, policy validation, tool actions, audit history, safe handoff, and evaluation. That design choice is strongly supported by primary literature. Self-RAG argues for adaptive retrieval and better citation quality; LongMemEval shows that long-term assistant memory remains difficult across sustained interactions; τ-bench shows that tool-using agents still fail on many realistic tasks; JourneyBench shows that customer-support agents need explicit policy-aware control; API-based agents outperform browsing-only approaches on realistic web tasks; RAGAS supports reference-free evaluation of retrieval pipelines; and AgentRewardBench shows why your evaluator dashboard must combine automated metrics with human transcript review rather than rely on a single scalar score. 

In practical terms, the frontend should be built as a workspace product with eight primary pages: Landing and Project Overview, Login and Team Dashboard, Project Setup, Conversation UI, Action Console, Audit and Handoff, Evaluator Dashboard, Admin and Test Harness, plus a final Submission Readiness page that validates whether the artifact is ready for the official FlowZint portal. The most important visual rule is that every resolution step should be inspectable: what the model believed, what it retrieved, which memory lane it used, which policy clause governed the decision, which tool call was attempted, and whether the final outcome passed evaluation. That transparency is strategically valuable both for judges and for debugging during the 30-day sprint. 

This report assumes several unstated facts. Team size is unspecified, so the frontend is designed for a small team of one to four builders with role-based workspace access. Budget is unspecified, so the recommendation is a pragmatic web stack that works on ordinary cloud budgets without custom model training. Preferred stack is unspecified, so I recommend a Typescript-first React stack with server-rendered public pages and client-heavy authenticated workspace pages. The public FlowZint page shows relative phases rather than absolute final dates in the fetched material, so this report treats your provided calendar as the operational schedule for planning while relying on the portal itself for the submission format and rubric. 

Event constraints and design assumptions
The official FlowZint portal is clear about the contest frame that matters for frontend decisions. The landing page emphasizes Sales Bot, Support Chat Bot, and Customer Care Bot, while the secure submission interface also exposes Open Innovation as a selectable track. The same interface shows team sizes up to four members, requires a project title, a project description of at least 50 words, a public demo video link, and a public source-code repository link, while treating the live project URL as optional. It also explicitly warns that private links or incomplete details can trigger rejection. For ResolveFlow, that means the frontend should support easy generation of screenshots, replayable transcripts, architecture evidence, and clean demo capture because these are not just presentation extras; they help satisfy the official submission format. 

The public rubric is equally important to the frontend. FlowZint weights Model Innovation and Novelty at 30%, Real-World Applicability at 25%, Technical Architecture at 25%, and Documentation Clarity at 20%. A hidden, black-box frontend would undersell architecture and documentation. A visible, inspectable UI that exposes evidence, policy checks, action traces, and evaluation outcomes is better aligned with the rubric because it turns backend sophistication into judge-visible proof. The frontend should therefore act like a “glass box” around the agent rather than a decorative shell. 

The contest page also shows a “4+ Weeks” structure with registration, build phase, submission, evaluation, and results as relative phases. Because the fetched portal does not itself surface absolute final dates in the visible text, this report uses your given 30-day full-time sprint as the schedule assumption. Technically, nothing in the architecture below depends on specific calendar dates; what matters is that the frontend is staged so that the conversation UI and action console exist by the middle of the sprint, while the evaluator dashboard, submission readiness checks, and demo tooling arrive before the final week. 

A second design assumption comes from the research rather than the event page: a winning customer-care agent needs visible support for memory, evidence, policy, tools, and evaluation. LongMemEval shows that long-term memory in chat assistants remains fragile, and τ-bench plus JourneyBench show that customer-support agents often fail on business-rule consistency and tool-reliability in realistic tasks. So the frontend should not compress everything into one chat feed. It should separate the conversation from memory, evidence, policy reasoning, and action state, while still keeping the whole experience coherent enough to demo cleanly. 

Frontend architecture blueprint
The recommended frontend is a hybrid SSR/CSR application. Public, judge-facing pages such as the landing page, architecture overview, public scenario replays, and documentation preview should be server-rendered for speed and linkability. Authenticated workspace pages such as the team dashboard, conversation UI, action console, evaluator dashboard, and admin harness should be client-rich and event-driven. This keeps the public demo fast while allowing the internal workspace to support streaming chat, incremental evidence rendering, tool-status events, scenario execution, and live evaluation results.

The architecture should be intentionally explicit about contracts. On the client, maintain six primary state domains: auth, workspace, conversation, actions, evaluation, and submission. Data fetching should be split between cacheable reference data such as teams, domain schemas, tools, and policy sets, and event-driven ephemeral state such as streaming responses, tool execution progress, and evaluator job updates. WebSocket or Server-Sent Events should drive the latter; regular query caching is sufficient for the former. This separation maps well to the research literature because the hard parts of agent UX are inherently stateful and multi-phase: retrieval and self-checking, long-term memory access, policy validation, tool execution, and transcript evaluation all have different latency and consistency needs. 

The guiding principle is API-first orchestration. The frontend should never directly “browse” external systems. Instead, it talks only to your ResolveFlow backend, which exposes typed endpoints for triage, retrieval, planning, policy validation, tool calls, memory operations, transcript export, and evaluation jobs. This is not only cleaner engineering; it matches the research signal that API-based or hybrid agents outperform browsing-only agents on realistic tasks. For the UI, that translates into visible tool cards, policy badges, and deterministic confirmations rather than brittle browser-automation animations.

A good mental model is to treat the frontend as three layers. The first is the operator layer for building and running the bot: project setup, conversation, actions, and audit. The second is the trust layer for proving that the bot is grounded and policy-compliant: memory lanes, evidence view, policy validation summary, and audit timeline. The third is the competition layer for converting the project into a winning submission: evaluator dashboard, replayable scenarios, and submission readiness. That separation makes the app easier to build and easier to narrate in the demo video.

Page-by-page frontend design
Landing and Project Overview
This page is the judge-first entry point. Its purpose is to explain in under two minutes what ResolveFlow does, which customer-care workflows it solves, why it is more than a chatbot, and where the viewer should click next. Because FlowZint explicitly scores documentation clarity and requires a public repo and demo video, this page should act like a polished “project brief” that compresses the architecture into understandable blocks without forcing the viewer into the live workspace first. 

The wireframe should be a clean three-zone layout. The header contains the project identity, track badge, and quick links to “Live Demo,” “Architecture,” “Scenario Replays,” and “Repo.” The middle section has a left-aligned hero statement and a right-aligned system snapshot card showing the pipeline: intake, memory, retrieval, policy, tools, audit, evaluation. Beneath that, use a four-card strip for the core differentiators: multi-issue intake, memory lanes, policy-aware actioning, and audit plus handoff. The lower half should show clickable replay cards for one easy scenario, one hard scenario, and one adversarial-user scenario.

The key components are HeroPanel, TrackBadge, ArchitectureSnapshot, CapabilityCards, ReplayGallery, and JudgeQuickLinks. The page consumes only light public data: project metadata, selected scenario replays, screenshots, and a compact metrics summary such as supported workflows and evaluation pass rate. State management should be minimal and mostly server-driven; cache aggressively and favor instant-first-paint.

The main UX flow is linear: understand the value proposition, see evidence that it is robust, then branch into either a replay or the live workspace. Error handling should degrade gracefully: if public replay data is unavailable, the page still loads the architecture and static screenshots. Accessibility should emphasize semantic headings, keyboard-navigable replay cards, strong focus states, and captions/transcripts for any embedded video previews. For the demo video, this page should support a “presentation mode” that enlarges architecture cards and hides secondary navigation.

Login and Team Dashboard
This page is the operational home for the builders. Because FlowZint permits up to four team members, the dashboard should be built around a small-team collaboration model: one owner role, several editors, and an optional viewer or demo role for judges or mentors. The frontend here should feel like a mission-control board, not a social dashboard. 

The wireframe works best as a two-column page. The left rail contains account and project switching, active domain, and last successful ingestion timestamp. The main column opens with the current project card, then a grid of operational summaries: “Latest conversation run,” “Policy coverage,” “Tool health,” “Evaluation trend,” and “Submission readiness.” Below that, show recent transcripts, pending action or policy warnings, and a team roster with presence indicators.

Key components include WorkspaceSwitcher, ProjectStatusCard, TeamRoster, RunSummaryGrid, RecentTranscriptsTable, and SubmissionHealthBadge. The data model is mostly workspace metadata: team, projects, last modified timestamps, upcoming tasks, last evaluation jobs, and unresolved ingestion or demo warnings. Primary APIs are POST /auth/login, GET /workspace, GET /workspace/projects, and GET /workspace/summary.

The UX flow begins with authentication, then lands on the most recent project. Empty-state design matters here: on first use, the dashboard should make “Create ResolveFlow workspace” and “Start project setup” the dominant calls to action. Error states should distinguish auth problems, missing workspace data, and stale ingestion state. Accessibility should ensure the dashboard cards are fully readable by screen readers and the status summaries are not color-only. For demo recordings, include a “clean mode” toggle that hides internal-only controls and leaves only the project signal cards visible.

Project Setup
This page is where ResolveFlow’s domain, schema, policy pack, tools, and memory configuration are defined. Conceptually, it is the only “builder-heavy” page; every other page should feel more operational. The reason to make setup explicit in the UI is strategic: JourneyBench and related work show that policy-aware support behavior depends on explicit control structures, not loose prompting. If the judge can see that you uploaded policies, mapped entities, and bound tools deliberately, your architecture becomes legible rather than implicit. 

The wireframe should use a stepper across the top: Domain, Schema, Policies, Tools, Memory, Test. The left side of the page shows the current step’s editor; the right side shows validation results, ingestion status, and a preview panel. In the Policies step, the builder uploads markdown, PDF-derived plain text, or structured JSON versions of rules and sees them parsed into policy nodes and allowed transitions. In the Tools step, the builder configures each tool contract and runs a health check. In the Memory step, the builder chooses how profile memory, episodic memory, and session summaries are extracted and displayed.

The core components are SetupStepper, DomainPicker, SchemaEditor, PolicyUploader, PolicyGraphPreview, ToolRegistry, ToolHealthTester, MemoryLaneConfig, and ValidationPanel. The main APIs are GET/POST /setup/schema, POST /setup/policies/upload, GET /setup/policies/graph, POST /setup/tools/register, POST /setup/tools/test, and POST /setup/memory/config.

The most important UX flow is progressive validation. Every step should have a “Save and validate” action that highlights schema mismatches, orphan policy steps, missing tool parameters, or missing memory labels. Error states should be precise and non-generic: “policy file parsed but 2 rule nodes are disconnected” is much better than “upload failed.” Accessibility should pay attention to code-editor alternatives, keyboard support in the graph preview, and text-first summaries of parse results. For demoing, allow instant loading of a seeded sample domain so the audience can see the configuration page without waiting for ingestion.

Conversation UI
This is the hero page. It should make ResolveFlow look like a resolution cockpit rather than a generic assistant. The central design problem is balancing readability with transparency. The layout that usually works best is a three-panel arrangement: a left sidebar for conversation list and issue chips, a central chat column, and a right-hand inspector with tabs for Memory, Evidence, Policy, and Actions.

The chat area should support multi-issue intake natively. Instead of collapsing the customer’s needs into one hidden intent, the first turns should produce visible issue chips such as “billing dispute,” “service outage,” and “cancellation risk.” Each chip can be focused, merged, or resolved independently. This matters because real customer care is often multi-threaded, and τ-bench plus JourneyBench both imply that single-turn, single-issue abstractions hide much of the true difficulty. 

The right inspector is where the research-backed value becomes visible. The Memory tab should present three lanes: Profile, Recent Sessions, and Episodic Facts. LongMemEval specifically emphasizes multiple memory abilities including temporal reasoning and knowledge updates, so the UI should not show “memory” as one blob. It should show what the agent thinks it knows about the user, when it learned it, whether it is current, and whether it is uncertain. The Evidence tab should show retrieved passages, their source labels, confidence, and which response span they support. This maps naturally to the motivation behind Self-RAG and RAGAS: retrieval should be inspectable, not invisible. 

The wireframe should therefore look like this in operation: the center column streams the conversation; beneath each assistant turn, inline citation pills open the supporting evidence drawer; a compact tool-event row appears when an action is planned or executed; the right panel shows synchronized tabs that follow the currently selected assistant turn. A sticky top bar should display the customer’s status, current risk level, consent status, and running resolution state. A bottom composer should support free text, canned system prompts for demo purposes, and a “simulate impatient user” toggle when in test mode.

The main components are ConversationList, IssueChipBar, ChatThread, MessageCard, CitationPill, MemoryLaneTabs, EvidenceDrawer, PolicySummaryCard, ToolEventRail, and ComposerBar. Primary APIs are POST /triage, POST /plan, POST /retrieve, POST /memory/read, POST /memory/write, and a streaming endpoint such as GET /conversations/:id/stream.

The core UX flow is: triage the user’s first message, render issue chips, stream the agent plan, reveal evidence and memory for each turn, and surface actions as proposed but not yet executed items. Error states should differentiate retrieval failure, memory read failure, tool gateway timeout, and policy-blocked action. Accessibility should include proper live-region handling for streaming tokens, clearly announced updates when a tool starts or finishes, visible keyboard shortcuts to open the evidence drawer, and a non-modal alternative to hover-only interactions. For demo-friendliness, include a “focus mode” that enlarges the chat and one-click highlights the exact evidence that supports the current answer.

Action Console
The Action Console is a separate page because action execution is the highest-risk part of customer care. The UI should make risky steps slow and visible, and harmless steps quick and obvious. τ-bench shows that task completion and reliability degrade sharply even for strong function-calling agents, and JourneyBench shows that policy-aware control changes outcomes materially. The frontend should therefore have a dedicated surface for proposed actions, policy checks, confirmations, execution state, and rollback or escalation outcomes. 

The wireframe should divide the page into a left “proposed action queue” and a right “selected action detail” pane. Each tool call appears as a card with the action name, target entity, required inputs, current policy status, and expected state mutation. Before execution, the card must show a policy badge such as allowed, allowed with confirmation, blocked, or requires escalation. If the action is confirmation-sensitive, opening the card should reveal the policy basis and a required affirmation step. After execution, the action card mutates into a result timeline with request, response, latency, downstream state changes, and links back to the originating conversation turn.

The main components are ActionQueue, ActionCard, PolicyBadge, ConfirmationModal, ToolParamsForm, ExecutionTimeline, and RollbackOrEscalatePanel. The primary APIs are POST /policy/validate, POST /tools/call, GET /tools/runs/:id, and optionally POST /tools/cancel for long-running operations.

The best UX pattern is simulate first, commit second. For important actions, the frontend should request a dry-run validation summary before the real tool call. Error states must be explicit about whether failure came from missing parameters, policy rejection, backend tool unavailability, or downstream business-rule mismatch. Accessibility requires that all confirmation steps be keyboard and screen-reader friendly and that policy explanations be textually described rather than icon-only. For demo mode, add a toggle to reveal the raw JSON request and response underneath each tool card without leaving the page.

Audit and Handoff
This page turns a completed or partially completed interaction into a trusted artifact. In customer care, not all conversations should end with full automation; some should end with a warm, high-quality handoff. The frontend should make this feel like a strength rather than a failure. The audit trail also makes the system more legible to judges because it shows every retrieval, policy decision, action, and user confirmation in one place.

The wireframe should have a large vertical timeline on the left and a sticky handoff summary card on the right. Timeline rows should include conversation turn, memory read, retrieval event, policy validation, tool invocation, outcome, and any error or escalation. Selecting a row should populate the handoff card with the relevant context: customer summary, issues addressed, actions attempted, evidence cited, and recommended next agent steps. There should be export actions for PDF, markdown, and replay link.

The main components are AuditTimeline, EventFilterBar, EventDetailPanel, HandoffCard, ExportControls, and CustomerSummaryHeader. Primary APIs are GET /audit/:conversationId, POST /handoff/generate, GET /handoff/:id, and POST /exports/create.

The UX flow is straightforward but important: review the conversation history, inspect what was done, generate or refine the handoff card, then export or share it. Error states should cover missing audit segments, handoff-generation delays, and export failures. Accessibility is mostly about making the timeline navigable by keyboard and ensuring that every event row has a readable text summary. For demo recordings, add a “playback mode” that animates the timeline from start to finish so the audience can see the whole run without scrolling manually.

Evaluator Dashboard
This page is where the product stops being “a bot” and becomes “a measured system.” RAGAS supports reference-free evaluation of retrieval pipelines, while AgentRewardBench shows that automatic judges alone are insufficient for reliable evaluation across agent trajectories. The frontend should therefore show at least three classes of evidence at once: task success outcomes, groundedness or retrieval metrics, and human transcript judgments. 

The wireframe should have a top strip of scorecards, a left panel for scenario sets and filters, a center table of run results, and a right detail pane for whichever run is selected. The top strip should include pass rate, policy adherence rate, average turns to resolution, tool-failure rate, and a compact RAGAS panel showing faithfulness or answer-groundedness indicators. The detail pane should show the full transcript, evidence links, tool history, human review notes, and whether the run was automatically or manually verified.

The main components are MetricCards, ScenarioFilterSidebar, RunTable, TranscriptViewer, EvidenceCorrelationPanel, HumanReviewPanel, and RagasSummaryCard. Primary APIs are POST /eval/run, GET /eval/runs/:id, GET /eval/runs, GET /eval/transcripts/:id, and POST /eval/review.

The UX flow should permit both breadth and depth. A builder should be able to spot regressions across many runs, then drill into one failed transcript and immediately see whether the problem came from retrieval, policy handling, tool execution, or user misunderstanding. Error states should distinguish missing metrics from unfinished jobs. Accessibility should include sortable table headers, screen-reader-readable metric descriptions, and transcript navigation landmarks. For demo use, expose a “judge summary” filter that reduces the dashboard to a compact set of three metrics and three representative transcripts.

Admin and Test Harness
This page is for controlled breakage. It exists because real users are not always cooperative, and the OpenReview paper on non-collaborative user simulators identifies four important adversarial behaviors: requesting unavailable services, digressing into tangents, expressing impatience, and providing incomplete utterances. This page should let the team run those behaviors deliberately against the system and compare outcomes over time. 

The wireframe works best with a left form-builder panel and a right live-run panel. The left side lets the builder choose a scenario template, attach a user persona, select one or more non-collaborative behavior presets, and specify stop conditions. The right side streams simulation progress, shows the current world state, and emits results into a batch table. A bottom drawer should list failed assertions and allow instant re-run from the failure point.

The main components are ScenarioBuilder, PersonaPresetSelector, NonCollaborativeBehaviorToggles, LiveRunStream, BatchRunTable, and FailureInspector. Primary APIs are POST /sim/run, POST /sim/users, GET /sim/jobs/:id, and POST /sim/batch.

The dominant UX flow is compose, run, inspect, rerun. Error states include malformed scenarios, simulator timeout, backend evaluator queue congestion, and missing ground-truth goal state. Accessibility should ensure the run stream is readable without animation dependency and that toggles are fully labeled. For demo-friendliness, include a one-click preset called “Impatient, incomplete, policy-sensitive” that reliably produces an interesting failure or safe recovery.

Submission Readiness
This page should be thought of as a pre-flight check, not as a replacement for FlowZint’s official submission portal. FlowZint’s portal requires a title, chosen track, project description of at least 50 words, public demo video link, public source-code repository link, and optionally a live project URL, and it warns that incomplete details or private links can cause rejection. Your internal submission page should therefore validate those same artifacts before the team submits externally. 

The wireframe should have a left checklist column and a right preview column. The checklist should cover title, selected track, project description length and quality, public repo reachability, public video reachability, optional live URL health, originality attestation, screenshot pack, and README completeness. The preview pane should show exactly what will be copied into the official portal fields, plus quick access to the replay links and architecture graphics likely to be used in the demo video.

The main components are SubmissionChecklist, PublicLinkValidator, DescriptionEditor, RepoHealthCard, VideoHealthCard, ArtifactPreview, and ExportPacketButton. Primary APIs are POST /submission/validate, POST /submission/export, GET /submission/status, and POST /submission/links/check.

The UX flow is validation-first: detect broken or private links, validate text length, preview the final packet, then export a clean submission bundle and checklist. Error states should be split between content completeness and network reachability. Accessibility should include explicit status text for each check and keyboard support for every validator action. For demo capture, expose a “recording safe” mode that hides personal account information and shows only the final checklist status.

State model, API contracts, and component system
The most pragmatic state-management approach is server state with TanStack Query plus a thin client store such as Zustand or Redux Toolkit for ephemeral workspace state. Query caching should own teams, projects, schema, policy graphs, tool registry, and evaluator run lists. The client store should own selected conversation, active issue chip, open inspector tab, streaming message buffers, currently proposed tool action, and “presentation mode” UI state. That split keeps the app debuggable and prevents streaming chat from polluting data caches.

For performance, use optimistic UI only where errors are cheap. Issue-chip creation, conversation bookmarking, and note editing can be optimistic. Tool execution, policy approval state, and submission validation should never be optimistic because false confidence is worse than slight latency. For offline or flaky-network tolerance, retain drafts locally, persist recently viewed transcripts, and provide a replay mode backed by previously exported JSON bundles so the demo still works even if the live backend is unstable.

These contracts intentionally return enough structure for the frontend to render explanations, not just outcomes. A good frontend for this project should never need to infer hidden business meaning from a raw string.

Delivery plan, security, performance, accessibility, and risks
The frontend plan should front-load the pages that make the system demoable early: Landing, Team Dashboard, Conversation UI skeleton, and Action Console skeleton. Project Setup and Audit should follow quickly, because they make architecture visible. The evaluator dashboard and test harness should arrive before the final week so that the demo and README can show evidence rather than aspiration. This is also the right order from a research standpoint: τ-bench and JourneyBench tell you that reliable actioning and policy control are the hard parts, while AgentRewardBench tells you not to postpone evaluation until the end.

On security and privacy, the frontend should assume the presence of PII and sensitive support data even if you are using mocked data in the hackathon demo. That means role-based route guards, expiring session tokens, audit logging on privileged actions, redaction in screenshot or replay export paths, and a clean separation between internal debug views and demo views. Tool execution pages should never expose secrets or raw backend credentials. If you show raw JSON in the demo, it should be a sanitized mirror of the request and response, not the live unfiltered payload.

For scalability and responsiveness, keep the frontend thin. Retrieval, policy validation, and tool execution should all stay server-side. The client should receive only structured summaries plus supporting detail on demand. Use WebSocket or SSE for streaming assistant responses and long-running tool or evaluation jobs because it simplifies progressive UI updates and makes the interface feel alive. Use polling as a fallback only for background evaluator jobs or when the deployment environment makes persistent connections unreliable. Conversation transcripts, evidence bundles, and evaluator runs should be paginated or virtualized once they grow large.

Accessibility should be treated as both quality and demo leverage. Screen-reader-readable evidence citations, keyboard-first navigation in the inspector, live-region announcements for streaming answers and tool status changes, and non-color-only status encoding will make the product feel far more mature. For video capture, add a presentationMode flag to enlarge typography, pin the evidence drawer, reduce motion, and hide internal builder toggles. Also add replayable transcripts with stable URLs and a “highlight evidence for current turn” control so the viewer always sees what supports the answer. These are small frontend choices, but they materially improve how trustworthy the product feels.

The clearest what not to build list is short. Do not build a single-column generic chatbot. Do not hide the policy layer. Do not rely on browser automation for core workflows when typed tool APIs are enough. Do not make every panel live at once if that turns the UI into visual noise. Do not defer evaluation pages until the end. And do not let the internal Submission Readiness page drift into a fake replacement for the official FlowZint portal; it should prepare and validate the artifact, then route the team to the official submission flow, which is the only valid submission path according to the portal. 

The single best summary of how the frontend should look is this: a clean, evidence-forward customer-care console with an inspectable mind. The conversation should remain central, but memory, evidence, policy, tool actions, audit, and evaluation should all be one click away and visually aligned with the active turn. That is the most convincing way to make ResolveFlow look like a serious, winning FlowZint Customer Care Bot rather than a polished wrapper around a language model. 

Open questions remain, but they are implementation questions rather than strategic ones: whether you want a telecom domain or a subscription-software domain, whether you want email magic-link or GitHub SSO, whether you want a relational store with a lightweight entity index or a dedicated graph store, and whether voice will be added later as a thin shell over this same frontend. None of those choices alter the core recommendation: build the frontend around visible resolution state, not around hidden model magic.
